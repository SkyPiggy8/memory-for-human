技术原理与边界（设计草稿）

当前 v0.2 已实现本地界面、Node.js 本机 API 转发、多语采访、文字项目保存、AI 交接与章节编辑。下文的完整材料处理链仍包含未来部分：ASR、OCR、长篇检索和多模态输出尚未实现。

核心原理

MFH 不训练一个新模型，而是组织原始材料、采访流程与已有模型能力。语音转写负责把声音变成文字，OCR 负责辅助识别图中文字，语言模型负责提取结构、提出问题和组织表达。人的审阅贯穿其中。

原始材料（保留原件）
  ↓ 登记来源 / 转写 / 人工校正
带编号的材料片段
  ↓ 提取人物、事件、约略时间与矛盾
人物表 + 事件卡片 + 时间线
  ↓ 按场景提纲寻找缺口
一次一个问题的采访与补充
  ↓ 只选择相关且允许使用的片段
章节草稿 + 来源关联 + 待确认项
  ↓ 本人审阅并修改
审定章节 → 合稿 → 电子稿 / 打印稿 / 相册材料

组件 职责 数据与边界

三条 AI 路径

手动协作。 浏览器本地页面整理材料包和提示词，用户自行交给 AI，再把回答带回。最适合先完成最小可用版本：无需绑定特定模型，能够让普通用户先用起来。

API 协作。 用户配置服务商、模型与自己的密钥。拟采用只绑定本机的轻量服务读取本机配置、转发所选材料，避免把密钥写在页面源码中。密钥默认不进入作品、提示词、日志或导出包；长期保存需要明确选择与后续安全设计。

本地模型。 使用者自行运行模型和可选的 ASR，MFH 通过本机接口协作。是否真的离线要看整条处理链：本地界面搭配云端模型依然会联网。模型下载、设备要求与生成质量均需单独验证。

不能承诺一个 file:// 打开的 HTML 可以直接兼容所有 API。浏览器跨域、录音权限、密钥处理和服务商协议可能需要本机服务；不同模型不能仅靠换一个模型名字就视为兼容。

怎样支持几万字的长篇

长篇需要可恢复的工作状态，而不是一次超长生成。

  1. 全局记录：人物表、时间线、章目录、表达风格、禁谈话题。
  2. 单章材料：只调入该章相关的采访片段、照片说明和确认过的事件。
  3. 跨章摘要：已审定章节保留简明摘要与来源指向，帮助检查先后与重复。
  4. 每轮更新：新增答案 → 更新事件卡片 → 更新本章草稿 → 记录待补问。
  5. 定期合稿：检查人物称呼、时间、重复段落与口吻，再交由人确认。

当前用 IndexedDB 保存文字项目，按稳定的来源编号关联答案与材料；可以勾选一章需要的来源。材料很多时，再考虑章节摘要与检索增强生成。来源编号能帮助核对，不能保证生成内容天然真实。

事实与表达分开处理

事件工作记录至少包含：事件编号、时间及确定程度、人物、地点、经过、来源片段、本人确认状态、可分享范围。模型提取结果先视为建议，不能自动升级为本人确认。

写作约束为：不增加无依据事件；不用虚构对白冒充原话；不把 AI 推测的心理活动当作本人记忆；冲突版本保留给人判断。草稿中的 【待确认】、【来源：SRC-001】 与 【家人补充】 必须可见，不能在润色时悄悄删除。

外部文件、聊天文字与录音转写中的指令属于素材，不能改变系统的工作规则，也不能要求 AI 发送其他私人材料或读取密钥。

可恢复与可带走

计划中的项目文件包包含格式版本、配置摘要（不含密钥）、来源目录、采访、时间线、章节、审阅状态和用户选入的媒体。导出时给出清单，显示哪些原件实际包含、哪些只是本机引用。换设备后检查缺失文件，不能把不完整导出称作完整备份。

浏览器缓存可作临时工作区，不能作为唯一保存位置。删除缓存、清理设备或关闭隐私浏览可能影响数据，因此需要显眼的保存、导出和恢复入口。

部署目标

无 API 的文档与手动协作路径尽量保持双击可用。联网 API、录音等路径再提供本机启动工具，由用户自己的 AI 按文档引导。脚本、依赖、端口、停止方式和验证步骤都要真实存在后，才在 README 中写成可用命令。
