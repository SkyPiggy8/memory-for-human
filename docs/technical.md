## 技术设计

MFH 要解决的是：怎样把一次聊天变成能长期继续的写作过程。人说过的话留在材料里，模型处理这次选中的内容，写出的章节再交回本人修改、确认。更换 AI、暂停采访或换一台电脑，故事也能继续写。

当前实现采用原生浏览器界面和 Node.js 本机服务。以下按 v0.2 实际代码说明。[参考项目与设计取舍](technical.md#related-work)另有介绍。

### 可以走完的写作流程

```text
回答问题 / 导入文字
        ↓
保留原文，分配来源编号 A… / M…
        ↓
使用者勾选本次需要的答案和材料
        ↓
准备任务与材料
   ├─ 复制给平时使用的 AI → 把结果贴回
   └─ 本机服务 → 自己配置的 API / 本地模型
        ↓
章节草稿：保留不确定说法，请模型附来源编号
        ↓
本人修改、核对 → 标为已审阅
        ↓
文字备份 / Markdown / 浏览器打印
```

六类故事使用不同的问题库。每种语言共 156 个起始问题，其中一生回忆有 48 个；接入 AI 后，再围绕已讲出的细节追问。问题库与提示词共同工作，尚未自动计算采访覆盖率，也没有把记忆抽成知识图谱。

### 来源可追溯：材料与章节分开保存

`app/core.js` 定义 `memory-for-human` v2 项目格式。采访答案、导入材料、章节分别存储。答案用 `A1`、`A2` 等编号，材料用 `M1`、`M2` 等编号。删除中间一项后，其他编号保持原样；备份和恢复也保留编号。

章节改了很多遍，仍能按编号回到当时的回答。导入材料默认不送给 AI，答案可以取消勾选。`context()` 只组装选中的内容，审阅时再附上当前章节。

写作提示要求关键事实带 `[A1]`、`[M1]` 等来源。程序保存编号和原文，但目前不会逐句验证模型是否引用正确。编号是核对入口，不能充当真实性证明。

### 模型解耦：同一份材料能交给不同的 AI

`taskPrompt()` 将任务分为采访、单章写作、审阅和用法解释。本机 API 调用使用这些约定；手动交接也带上相应规则、语言和选中的材料。使用者可以继续用熟悉的聊天工具，不必先申请开发者账号。

API 路径由 `server.mjs` 转发。OpenAI 兼容协议与 Anthropic Messages 分别适配，服务商、模型和地址可以配置。本地模型需要使用者先运行兼容接口。MFH 使用现有模型，没有训练自己的基础模型。

两条路径的共同结果是可编辑章节。手动带回的普通文字或约定 JSON 会新增一章，默认草稿。换模型时，材料和旧章节仍在本地工作区中。

### 人工审阅：确认状态跟着章节走

每章保存来源类型、内容、更新时间和 `approved` 状态。AI 生成、手动贴入或原文整理出的章节，初始都是草稿。本人核对后可以标为已审阅；再次修改，状态回到草稿。

AI 审阅任务会找无依据的细节、时间冲突和隐私问题，返回需要检查的句子。它没有批准章节的权限。当前确认状态针对整章，还没有逐条事实的确认表。

材料中的命令按素材处理，不能改变写作规则，也不能获得读取其他项目或密钥的权限。这一约定写入提示词；尚未做完整的提示注入对抗评测。

### 可恢复的数据：保存进度，留出搬迁入口

`app/app.js` 用 IndexedDB 保存多本回忆录，包括回答、导入文字、草稿、当前章节和未提交的回答。`publicProject()` 按字段导出，API Key 不属于项目格式。

每次写入在同一个 IndexedDB 读写事务中比较加载的完整记录，再保存带有新 `_mfhRevision` 的版本。同页写入依次执行，旧记录在首次实际保存时补上版本；仅打开已有作品不会写回。版本元数据不进入文字备份或 AI 上下文。

另一标签页已保存时，本页停止写入并保留文字，显示三语提示及本页备份入口，禁用覆盖式重试；新建、切换或导入也不会丢弃未保存的当前书稿。先保留各页所需的文字备份，再关闭其他标签页、刷新最新版本并手动整理差异。恢复备份会新增一本书，不自动合并。普通存储失败可以重试。冲突在尝试保存时发现；已打开的旧版页面没有此保护，更新后请先关闭旧版页面。

恢复时，`validateProject()` 检查格式、版本和大小，为恢复的项目生成新身份，原项目保留。过大的材料明确报错，不在后台截短。稳定来源编号保留引用，新项目身份避免覆盖；两者各有用途。

这是文字项目备份。照片、录音和扫描件没有装进 JSON，必须另存。IndexedDB 没有加密；不同浏览器、端口和文件模式分别保存数据，迁移前需要下载备份。

### 本机运行：减少依赖，分开作品与密钥

前端是 `index.html` 和 `app/` 中的经典脚本，无需构建。双击 HTML 可以填写、整理和备份。API 使用 Node.js 22+ 本机服务，只依赖内置模块，监听 `127.0.0.1`。

Windows 启动器优先使用现有 Node.js，缺少时下载官方 LTS，核对 SHA-256 后解压。运行环境留在项目的私有目录中。

服务检查 Host、Origin 和本次运行的会话令牌；静态文件按允许范围提供，私有配置不对网页开放。页面填写的 Key 默认只放在服务内存里，关闭后失效。服务商报错经过处理再返回，避免原样展示上游响应中的敏感内容。[隐私说明](guide.md#privacy)列出数据去向。

### 长篇写作的办法和限制

当前逐章写作：选一章的材料，完成草稿和审阅，再继续下一章。目标篇幅只是参考，不为凑够字数补出经历。

提交的材料 JSON 超过 100,000 个字符时，程序提示减少材料、拆章处理。这个限制按字符计算，没有按各模型的 token 上限自动分配预算。生成达到输出上限时，提示会保留在结果中，截断稿不能当作完整章节。

几万字作品还需要人工管理跨章时间、称呼和重复内容。目前没有自动摘要、语义检索或全书一致性校验。下一步应先建立可审阅的事件卡与章节索引，再考虑检索，避免把检索到的片段误当作已确认事实。

### 代码与设计选择

| 位置 | 工作 | 原因 |
| --- | --- | --- |
| `app/core.js` | 项目格式、校验、选材、任务规则、导出 | 浏览器与测试共用规则，减少保存和恢复的差异 |
| `app/app.js` | 采访、保存、章节操作、交接、打印 | 进度留在作品里，暂停后能继续 |
| `app/i18n.js` | 三语界面、解释与问题库 | 讲述者与协助者使用同一套流程 |
| `server.mjs` | 本机会话、协议适配、转发、错误处理 | 将 Key 与作品分开，减少运行依赖 |
| `docs/templates.md`、`docs/ai-handoff.md` | 采访与写作说明 | 自己的 AI 或家人也能接手 |

核心与服务测试覆盖备份、选材、大小限制、本机访问控制和模拟 API 传输。真实浏览器检查覆盖填写、三语切换、交接、恢复、编辑与打印。真实模型的追问质量、长篇效果和各账号的连通性需要分别验证。

### 后续技术工作

音频转写要保存原音位置并提供校对入口；OCR 要保留原图与识别文本；多人讲述要记录各自版本和确认人。成品排版需要实际打印样本。这些都是后续开发，现有文字导入和打印按钮还不能完成它们。

## 接口依据和验证范围

接口资料查阅于 2026-10-12。页面预设方便开始，模型名称可以修改。是否开通、是否有额度、当地能否连接，要看使用者自己的账号和服务。

| 服务 | 实现依据 | 本项目请求方式 |
| --- | --- | --- |
| OpenAI | [Chat Completions](https://developers.openai.com/api/reference/resources/chat)、[GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini) | `/v1/chat/completions`、Bearer Key |
| DeepSeek | [首次 API 调用](https://api-docs.deepseek.com/) | `/chat/completions`、Bearer Key，预设 `deepseek-flash` |
| Claude | [Messages API](https://platform.claude.com/docs/en/api/messages/create)、[模型目录](https://platform.claude.com/docs/en/models/overview) | `/v1/messages`、`x-api-key`、版本头；独立适配 system 与 content |
| 豆包 / 方舟 | [官方上下文与 Chat API 示例](https://docs.volcengine.com/docs/ark/context-management?lang=zh) | `/api/v3/chat/completions`、Bearer Key；模型或 Endpoint ID 以账号开通情况为准 |
| 自定义 / 本地 | 使用者提供的 OpenAI Chat Completions 兼容接口 | 本地 HTTP 或远程 HTTPS，明确输入模型名称 |

项目选择 Chat Completions 以复用兼容服务，Claude 使用独立 Messages 适配；不把所有服务都当成同一种协议。

### 模拟服务和浏览器检查

本机静态服务、会话认证、来源限制、配置验证、OpenAI 格式与 Claude 格式的请求和解析、密钥不进入对外配置响应、服务商错误内容不回显，以及断开连接。验证使用模拟响应，不向真实服务发送私人材料或真实 Key。

浏览器验证覆盖三语切换、采集和编辑、AI 结果导入、文字备份恢复、Markdown、打印稿和解释/交接入口。语音输入依赖设备与浏览器，没有在每个设备上实测；Windows 首次下载路径需要实际联网下载条件。

### 需要真实使用再确认的部分

目前没有逐一实测使用者真实账号的余额、模型权限和地域连通性，也没有完成长时间、大规模真实采访。兼容服务的参数支持还需分别核对。

服务仅监听 `127.0.0.1`。在线调用时所选内容会发给配置的服务；Key 默认保存在服务运行内存中，不保存在浏览器项目或导出包。可选本机配置文件由使用者另外提供。

## 参考项目与设计取舍

写回忆录，难处往往出现在开始之前和写完之后：家人不知道怎么提问，讲述者记不清年份，旧材料散在不同地方，稿子写好后又不知道怎么保存、打印。MFH 把这些步骤接在一起，面向能讲故事、但不想研究开发环境的使用者。

这次参考了三个项目。StorySage 与 memoir 的说明和部分源码查阅于 2026-10-13，下面给出固定提交链接；没有运行它们，因此不比较实际效果、速度或模型准确率。Lorevox 的当前链接无法读取，单独注明资料范围。

### MFH 把工作放在哪里

**让平时使用的 AI 能接手。** 使用者可以复制任务说明和选中的材料，交给自己的聊天工具，再把章节带回来。API 是另一条入口。项目格式和作品保存独立于这两种使用方式，所以不必在开始采访前选定一个服务商。

**按关系组织采访。** 恋人、婚姻、老人一生、战友、同事和同学各有提纲与问题。恋人的一段普通日常，和老人跨几十年的生活经历，需要不同的问法和章节跨度。三种语言目前各有 156 个起始问题，AI 再接着具体回答补问；这部分没有做成自动采访规划器。

**让家人能代操作。** 讲述者可以只负责讲，家人负责记录和读回核对。通俗解释、安装交接和章节回贴都有入口；前端无需构建，Windows 有运行环境准备脚本。这些工作服务于实际操作，不要求讲述者理解 agent、数据库或 token。

**把可带走的作品做完整。** 稳定来源编号、勾选材料、章节修改后重新审阅、追加式恢复，以及文字备份、Markdown、打印和制作清单，都围绕“写完之后怎样继续改、怎样交给家人”设计。照片书、硬件相框和 NAS 提供准备与制作步骤，尚未自动集成。

来源保留、本人确认、本地保存和 AI 采访在其他项目中也有体现；它们不是本项目独有的发明。MFH 的特点在于把六类关系、三语协助、自己的 AI、低依赖本机运行和成品制作放进同一套家庭写作流程。

### 目前的技术侧重点

本页说明设计位置，不把文档里没看到的功能判定为对方没有，也不据此宣布整体领先。下一步应找家庭使用者实际完成一章，观察哪些问题能问出细节、哪一步容易丢进度，再用结果改进流程。
